# 日志与可观测性规范

日志的目标是让开发、测试和生产问题能够按一次请求、一个用户动作或一个后台任务完整还原，同时避免重复、噪声和敏感信息泄露。本规范是代码评审与上线验收的强制要求。

## 1. 技术方案

- Spring Boot 使用 SLF4J API 和 Logback 实现，不直接依赖具体日志实现类。
- 生产环境输出单行 JSON，local 环境允许使用便于阅读的文本格式。
- Nuxt SSR 使用统一服务端 Logger，字段名称与后端保持一致；禁止在生产服务端使用零散 `console.log`。
- 浏览器端只保留必要的开发日志；生产环境不向控制台输出 Token、用户数据、接口响应体或内部异常详情。
- 日志时间统一使用 UTC ISO 8601，展示和检索工具可转换为 Asia/Shanghai。

## 2. 统一字段

每条应用日志至少包含：

| 字段 | 说明 |
|---|---|
| timestamp | UTC 时间，精确到毫秒 |
| level | DEBUG、INFO、WARN、ERROR |
| service | 服务名，如 forum-api、forum-web |
| environment | local、test、staging、production |
| logger | Logger 或类名 |
| message | 简洁且稳定的事件说明 |
| requestId | 单次入口请求标识 |
| traceId、spanId | 启用链路追踪后的关联标识 |
| userType、userId | 已认证主体类型与 ID；未登录时为空 |
| route、method | 规范化路由和 HTTP 方法 |
| status、durationMs | 响应状态和耗时 |
| errorCode | 业务或系统错误码 |

禁止把原始查询参数和完整 URL 直接写入日志；需要记录时只保存白名单字段，搜索词、邮箱和自由文本不得进入普通日志。

## 3. 请求链路

- 边缘代理接受合法的 `X-Request-Id`，否则生成新的不可预测标识；来自非受信来源的异常值应被替换。
- Nuxt SSR 将 requestId 传递给 Spring Boot；Spring Boot 使用 Servlet Filter 放入 MDC，并在响应中返回 `X-Request-Id`。
- Filter 必须在请求结束时清理 MDC，避免线程复用造成串号。
- 异步任务、线程池、邮件 Outbox 和定时任务必须显式传播或创建 traceId/requestId，不能依赖普通 ThreadLocal 自动传递。
- 前端错误上报只携带错误类型、页面、发布版本和 requestId，不上传正文、Token 或个人信息。

## 4. 日志级别

- `ERROR`：未预期异常、数据一致性失败、邮件进入死信、迁移或关键任务失败。必须包含异常堆栈和稳定 errorCode。
- `WARN`：可恢复异常、限流命中、乐观锁冲突、外部服务重试、可疑认证行为。正常参数校验不应大量记录 WARN。
- `INFO`：应用启停、发布版本、关键业务状态变更、后台管理操作、定时任务摘要和外部调用结果摘要。
- `DEBUG`：开发诊断细节。生产默认关闭，临时开启必须限时、限包并经过授权。
- 禁止在循环中逐条输出 INFO/ERROR；批处理记录开始、结束、数量、耗时及失败摘要。

## 5. 分层记录规则

### Controller 与入口 Filter

- 入口 Filter 统一记录请求完成事件：规范路由、方法、状态码、耗时、requestId 和认证主体。
- Controller 不重复记录“进入方法/返回结果”，不打印 DTO、VO 或完整请求体。
- 参数校验失败由全局异常处理器记录摘要；高频 4xx 使用 INFO 或受采样的 WARN。

### ServiceImpl

- 仅记录具有业务意义的状态变化，例如审核、锁帖、用户禁用、权限变更和恢复内容。
- 业务日志包含资源 ID、操作结果和稳定事件码，不记录正文、驳回自由文本或用户邮箱。
- Service 捕获异常后若不能处理，应继续抛出，不要记录一次后由全局处理器再次记录。

### Mapper 与 SQL

- 生产环境禁止打印 SQL 参数和值，尤其是密码哈希、邮箱、Token 哈希和正文。
- 普通 SQL 不逐条记录；只通过数据库或连接池能力记录超过 500ms 的慢 SQL摘要、Mapper 方法和耗时。
- 慢 SQL 日志不得展开大字段或用户输入；执行计划在受控诊断环境单独采集。

### 安全、邮件和后台任务

- 登录、Token 重放和限流等安全事件写入结构化安全日志；需要持久追责的账号禁用、权限变更等操作同时写入 `audit_log`。
- 管理操作写入 `audit_log`；应用日志记录审计日志 ID，不以普通日志替代持久审计。
- 邮件只记录 outbox ID、模板编码、密钥版本、状态、重试次数和提供商错误码，不记录或解密输出收件地址、模板参数和邮件正文。
- 定时任务记录 jobName、executionId、开始/结束时间、处理数量、成功数、失败数和耗时。

## 6. 异常处理

- 全局异常处理器是 HTTP 请求完整堆栈的唯一记录位置。
- 已知业务异常返回稳定业务错误码，通常不记录堆栈；未知异常记录一次完整堆栈并返回通用错误信息。
- 数据库异常对外转换为统一错误码，日志保留异常类型和约束名，不输出 SQL 参数。
- 外部服务异常记录提供商、操作类型、耗时、HTTP 状态和提供商错误码，响应体仅在确认不含敏感信息且经过截断后记录。
- 日志消息必须参数化，例如 `log.info("post reviewed: postId={}, result={}", postId, result)`，禁止字符串拼接和序列化整个对象。

## 7. 严禁记录的信息

- 明文密码、密码哈希、验证码和密码重置链接。
- Access Token、Refresh Token、JWT、Cookie、Session ID、CSRF Token和 API Key。
- 完整邮箱、完整 IP、邮件密文解密结果和第三方凭据。
- 帖子正文、评论正文、个人简介、举报描述和审核备注全文。
- 完整请求体、响应体、Authorization Header 和数据库连接串。

必须记录邮箱或 IP 的关联信息时，使用项目专用密钥加盐的稳定哈希；展示信息最多使用脱敏片段。密钥不得写入日志或数据库配置表。

## 8. 文件、采集和保留

- 容器环境优先输出 stdout/stderr，由日志平台采集；不得依赖容器本地永久文件。
- 非容器环境使用按天且按大小滚动的文件，单文件建议不超过 100 MB，并设置磁盘上限。
- 应用日志默认保留 30 天，安全事件 90 天，审计日志 180 天；到期清理必须可审计。
- ERROR 日志和审计日志访问应按最小权限控制，下载与导出行为需要记录。
- 日志平台传输和存储启用加密，并限制开发人员直接访问生产日志。

## 9. 告警与降噪

- 对 5xx 比例、未捕获异常、数据库连接池耗尽、慢 SQL 激增、邮件死信、Token 重放和定时任务失败设置告警。
- 同一异常按 errorCode、异常类型和规范路由聚合，避免每次请求产生一条告警。
- 健康检查、静态资源和正常 404 应采样或降级记录。
- 告警必须包含环境、服务、版本、首次/最近发生时间、次数和可搜索的 requestId 示例。

## 10. 验收检查

- 任一失败请求可通过返回的 requestId 找到 Nuxt 与 Spring Boot 对应日志。
- 未知异常只出现一次完整堆栈，业务异常不会产生大量 ERROR。
- 异步邮件和定时任务具有独立 executionId，并能关联到触发业务。
- 自动化扫描确认日志不存在敏感字段；测试使用标记值验证密码、Token、Cookie、邮箱和正文不会落盘。
- 压测期间日志吞吐不会成为主要瓶颈，日志平台不可用时应用具备有界缓冲或安全降级行为。
